Release should not proceed as-is. The evidence shows multiple concrete defects across API, store, worker, and Bridge that can corrupt identity, violate immutability, or misapply a remote effect.

**Prioritized defects**

1. **API scopes operation keys globally instead of per Task**
   - Evidence: `review-api` lines 8-9 use `results.byOperationKey(body.operationKey)`, and `review-store` defines `byOperationKey(key)` as `SELECT * FROM results WHERE operation_key=? LIMIT 1`.
   - Impact: `review-observations` A shows Team Blue received the Red Result ID for the same key on a different Task. That violates `review-rules` and can leak cross-team data.
   - Minimal repair: change lookup to `byTaskAndOperationKey(task.id, body.operationKey)` and preserve immutable insert/conflict behavior per Task.
   - Regression: same key on two Tasks returns two distinct Results; same Task + same key + different body conflicts.

2. **Result bodies are mutable after acceptance, and accepted source identity is not fixed**
   - Evidence: `review-store` `save()` does `ON CONFLICT(task_id,operation_key) DO UPDATE SET body_json=..., body_digest=...`; `review-api` inserts acceptance on `body.review.reviewerApproved`; `review-observations` B says the `body_digest` changed after a human accepted the first body.
   - Impact: violates `review-rules` immutability of Result bodies and accepted source identities.
   - Minimal repair: replace update-on-conflict with immutable insert/conflict rejection or append-only versioning keyed by a new Result id; acceptance must bind to the originally stored Result id and body digest.
   - Regression: second submission with same task/key but different body is rejected or creates a new immutable Result; accepted Result content cannot change.

3. **Delivery claim is not atomic, allowing duplicate workers on the same delivery**
   - Evidence: `review-store` says `claim()` SELECT and UPDATE are not in a transaction; `review-observations` C shows two claims on the same delivery both returned pending.
   - Impact: two workers can invoke Bridge for one delivery, causing duplicate external effects or conflicting receipts.
   - Minimal repair: make claim a single atomic conditional update/CAS, or wrap SELECT+UPDATE in a transaction with a state predicate.
   - Regression: concurrent claim attempts yield exactly one worker owning the delivery.

4. **Worker chooses the latest artifact revision instead of the accepted one**
   - Evidence: `review-worker` line 5 uses `artifacts.latest(result.body.artifactId)`; `review-rules` require exact accepted Artifact ID, revision, and digest; `review-observations` D shows revision 8 appeared after queueing an accepted revision 7.
   - Impact: the handoff can silently switch to the wrong revision.
   - Minimal repair: fetch the exact accepted artifact reference from the accepted Result, not `latest()`, and verify id/revision/digest match the accepted record.
   - Regression: if revision 8 appears after acceptance of revision 7, dispatch still uses revision 7.

5. **Grant freshness is not revalidated at the last moment**
   - Evidence: `review-worker` uses `grantCache.forDelivery(d.id); // approved and valid at enqueue`; `review-operations` requires revoked grants to fence not-yet-started effects and immediate revalidation before local effect; `review-observations` E shows expiration and revocation before dispatch.
   - Impact: a revoked/expired grant can still authorize a dispatch.
   - Minimal repair: re-read grant authority immediately before Bridge call and fail closed if expired/revoked.
   - Regression: dispatch after revocation/expiry is blocked.

6. **Bridge does not pass expectedHead into the external CAS**
   - Evidence: `review-bridge` checks `RefHead(binding, x.Ref)` then calls `ExternalApply(...)` without `expectedHead`; `review-observations` G shows ref changes between the precheck and apply.
   - Impact: another writer can race the ref update, so the precheck is stale.
   - Minimal repair: pass `expectedHead` into `ExternalApply` and treat mismatch as conflict.
   - Regression: ref changes between check and apply cause a conflict, not a write.

**Controls already correct**

- API rejects wrong team and wrong Run association (`review-tests`).
- Digest syntax and unknown fields are rejected (`review-api`, `review-tests`).
- Worker only proceeds when acceptance exists (`review-worker`).
- Bridge rejects unrecognized repository and wrong transport pin (`review-tests`, `review-bridge`).
- Exact bytes/digest comparison is already present in API and Bridge (`review-api`, `review-bridge`).

**Residual uncertainty**

- `review-api` inserts acceptance when `review.reviewerApproved` is true, but the evidence does not fully show whether that path is intended only for observations or also for final acceptance authority. The safe reading is that it must not grant acceptance authority beyond the human Owner rule in `review-rules`.

**Regression matrix**

- Cross-Task same key: expect distinct Results, no data leak (`review-observations` A).
- Same Task same key different body: expect conflict or immutable new version, never in-place rewrite (`review-observations` B).
- Concurrent claims: expect exactly one winner (`review-observations` C).
- Accepted artifact superseded later: expect original revision/digest to be used (`review-observations` D).
- Grant expired/revoked before dispatch: expect dispatch blocked (`review-observations` E).
- Lost remote reply / retry: expect reconciliation by retained remote key, not fresh replay (`review-observations` F, `review-operations`).
- Ref changed after precheck: expect CAS conflict (`review-observations` G).

The release should **not proceed** yet.

**Prioritized defects**
1. **Bridge current-authority gap**: `review-bridge` shows `RefHead(binding, x.Ref)` is checked before `ExternalApply`, but `ExternalApply` only enforces atomic expected-head CAS when `expectedHead` is supplied, and this call path does not pass it. That makes the local precheck insufficient against a concurrent writer.
   - Repair boundary: require `expectedHead` in the external apply path and make it authoritative, not advisory.

2. **Store claim race**: `review-store` indicates `claim` uses separate `SELECT` and `UPDATE` statements, and concurrent callers can race. That can double-dispatch one delivery and break lease/generation assumptions.
   - Repair boundary: make claim atomic with a transaction or single guarded `UPDATE ... WHERE state='pending'`.

3. **Worker timeout reconciliation gap**: `review-worker` says a remote effect can complete before the Central reply, but the timeout path discards no remote receipt and lacks read-only reconciliation. That can requeue an already-applied effect.
   - Repair boundary: reconcile by retained receipt/key before requeueing.

4. **API acceptance authority needs to remain non-authoritative**: `review-api` correctly validates task/team/agent membership, run ownership, artifact binding, and digest match, but `review.reviewerApproved` is only an observation and does not itself grant authority.
   - Repair boundary: keep this field observational only; do not let downstream code treat it as proof of authorization.

**Controls already correct**
- API enforces task/team/agent/run/artifact/digest alignment before saving: `review-api`.
- Closed result schema rejects unknown fields: `review-api`.
- Bridge verifies pinned transport and repository registration before apply: `review-bridge`.
- Bridge checks artifact digest locally before external apply: `review-bridge`.
- Worker requires an acceptance record before dispatch: `review-worker`.
- Existing tests cover malformed digest rejection, unknown JSON property rejection, unrecognized repository, wrong transport pin, one-worker claim behavior, and successful remote completion: `review-tests`.

**Supported defects from the discussion transcript**
- Same op key across tasks can return the wrong Result: `review-observations` A vs `review-rules`.
- Accepted Result body can mutate after human acceptance: `review-observations` B vs `review-rules`.
- Bridge dispatch can use latest revision instead of the exact accepted artifact: `review-observations` D vs `review-rules`.
- Grant expiry/revocation can fail to fence a not-yet-started effect: `review-observations` E vs `review-rules` and `review-operations`.
- Lost-response retry can mint a fresh remote key instead of reconciling the retained one: `review-observations` F vs `review-operations`.

**Regression matrix**
- Same op key, different task, different body -> conflict; no Result reuse.
- Concurrent same key, same task, different bodies -> exactly one accepted body; the other conflicts/fails immutably.
- Artifact revision advances after acceptance -> Bridge uses accepted revision/digest, not latest.
- Grant expires or is revoked after enqueue but before dispatch -> dispatch blocked.
- Remote call times out after write -> reconcile via retained remote key, not fresh-key replay.
- Concurrent claim on one delivery -> exactly one winner, no duplicate dispatch.

**Conclusion**
The evidence supports a **blocker** decision. The strongest demonstrated issues are current-authority enforcement in Bridge, atomicity in claim/accept paths, and timeout reconciliation. The main unresolved implementation question is whether the Bridge external apply API must hard-require `expectedHead`; that appears necessary for correctness, but the exact code change boundary is still open.

Release should not proceed as-is.

Prioritized defects, with evidence:
1. Cross-task identity leakage in `review-store`.
   - `byOperationKey(key)` looks up only `operation_key` and ignores `task_id`, while `results` is unique on `(task_id, operation_key)`. That allows one task to receive another task’s result when the same operation key is reused.
   - This is a demonstrated source-identity bug, not a hypothesis.

2. Concurrent claim race in `review-store`.
   - `claim(id, now)` performs `SELECT` and `UPDATE` without a transaction, and the evidence says two workers can call `claim` concurrently with no per-delivery lock.
   - Result: double-claim or split-brain dispatch is possible.

3. Timeout reconciliation gap in `review-worker`.
   - The evidence says a remote effect can complete before the central reply, but the timeout path “discards no remote receipt” and has no read-only reconciliation step.
   - Result: central state can remain stale even though the external side already applied the operation.

4. Incomplete current-authority enforcement in `review-bridge`.
   - It checks `RefHead(binding, x.Ref) == x.ExpectedHead`, but `ExternalApply` is called without `expectedHead`, even though atomic CAS only happens when `expectedHead` is supplied.
   - The evidence also says transport pinning authenticates a peer, not a task-specific owner grant, so current authority is not fully enforced.

5. Accepted-result immutability appears broken.
   - `review-rules` says result bodies and accepted source identities are immutable, while `review-observations` says concurrent submissions left one result ID but `body_digest` changed after human acceptance.
   - If that reading is correct, accepted evidence can be rewritten after acceptance.

6. Artifact pinning is not strong enough at handoff.
   - `review-rules` requires the exact accepted artifact ID, revision, and digest, but `review-observations` says a later revision existed before dispatch.
   - Without persisting the accepted tuple at decision time, Bridge can ship the wrong revision.

7. Owner consent is not revalidated immediately before local effect.
   - The evidence says consent must be bound to repository, Task, Run generation, destination, and expiry, with immediate revalidation before local effect.
   - `review-observations` says a grant expired and was revoked before dispatch, yet dispatch still occurred.

Controls already correct:
- `review-api` constrains task/team/agent membership, run ownership, artifact team/run binding, and digest verification before saving.
- `review-api` rejects unknown fields and treats `review.reviewerApproved` only as an agent observation, not acceptance authority.
- `review-bridge` verifies repository registration, digest, and current ref head before attempting apply.
- `review-tests` reportedly cover foreign team actor rejection, malformed digest rejection, unknown JSON rejection, one-worker claim behavior, artifact-byte digest checking, successful completion marking, unrecognized repository rejection, and wrong transport pin rejection.

Minimal repair boundaries:
- `review-store`: key result lookup by `(task_id, operation_key)` and make `claim` atomic with a transaction or single conditional update.
- `review-worker`: add timeout reconciliation using the retained remote receipt before re-queuing.
- `review-bridge`: pass `expectedHead` into `ExternalApply` and add a task-bound authorization check separate from transport pinning.
- For immutable acceptance and artifact pinning, persist the accepted body/hash and accepted artifact tuple at decision time, then refuse later mutation or drift.

Regression matrix:
- Reused `operation_key` across tasks -> task-local lookup only; no cross-task result leakage.
- Two workers claim the same delivery concurrently -> exactly one winner.
- External apply succeeds but reply times out -> reconciliation marks completion; no duplicate dispatch.
- Ref advances between read and apply -> CAS conflict, not blind overwrite.
- Valid pinned peer but wrong task grant -> authorization failure.
- Accepted artifact revision changes after queue -> dispatch still uses the queued accepted tuple.
- Grant expires or is revoked before dispatch -> final pre-effect check aborts.

Bottom line:
- The release cannot proceed yet.
- The strongest demonstrated defects are identity isolation, claim concurrency, worker reconciliation, and bridge authority/CAS handling.
- The main unresolved question is whether any additional out-of-band authorization or reconciliation controls exist outside the reviewed API/store/worker/bridge modules; none are evidenced here.
