# QA-070 复杂任务实测与逐项评价

## 结论

2026-09-06 已用三道新构造的复杂工程题，各安排两次单 Agent / Discussion
对照。原定 12 个试验臂全部尝试一次，共 22 次真实模型调用、22 个实际 Run，
没有重跑失败项。保留 9 份最终答案、3 个失败试验臂，形成 3 组完整配对，
另有 3 份未配对答案。不能把本轮称为六组完整对照。

在完整配对中，单 Agent 为 **45/60**，Discussion 为 **22/60**；分别使用
**3 / 9 个 Run**，试验臂累计耗时 **140.228 / 202.479 秒**。本轮没有观察到
当前 Discussion 配置在这些复杂任务上的交付收益。9 份答案都未通过预先冻结
的关键验收要求，包括得分最高的单 Agent 答案。因此，分数领先不等于结果
可直接执行，也不能把单 Agent 描述为已经解决了这些任务。

题目复杂度提高后仍未出现收益，削弱了“之前只是题目太简单”这一解释。
但本实验同时改变了信息在成员间的分配方式：单 Agent 可直接读取全部资料，
Finalizer 只能直接读取 Reviewer 的一半资料，另一半依赖贡献内容。
观察到的是这一完整配置的效果，不能单独证明所有多 Agent 协作都没有价值，
也不能单靠本轮分数决定删除产品功能。

建议继续冻结功能扩张，日常任务先使用单 Agent 并执行明确验收；确有独立
资料或职责需要汇合时保留显式协作选择。不要把“复杂任务”本身作为启动
Discussion 的理由，也不应继续针对这些已评分题目反复调参寻找胜局。
删除功能还需要结合实际使用、维护负担及依赖关系决定，本轮没有执行删除。

[冻结题包](fixtures/qa-070-complex-cases.json)，在真实调用前的 `ebe5e74`
提交固定。本轮用的是有意构造的工程挑战，不是真实客户事故或线上变更。

单个任务有 10 项标准，每项 0/1/2 分，总分 20。得到 16 分及以上，且所有
标为 critical 的项目均为 2 分，才算这份诊断或方案达到题包验收。
参考排程和评分答案没有提供给模型。没有执行模型生成的补丁或迁移操作。

## 比较方法与可比性边界

- 每题两次预定重复，第二次反转单 Agent / Discussion 的执行顺序；失败不重试。
- 两边请求同一 `gpt-5.4-mini`、low effort；没有 Provider 签署的实际模型身份证明。
- 两边收到相同任务、现有事实审查要求和最多 900 英文词的最终交付要求。
- 单 Agent 一次 Run，可读全部 8 份资料。Discussion 是 Solver 与 Reviewer
  各读互不重叠的 4 份，再由 Reviewer Finalizer 汇合，完整交付需要 3 个 Run。
- 每次调用最多 8 次固定 ID 读取，没有 shell、浏览器或任意文件读取。允许的
  资料读取工具是 `evidence.read_evidence`；不允许资源列表等其他工具调用。
- Finalizer 可直接读自己的 4 份资料，并得到双方被接受的贡献。团队资料并集
  与单 Agent 相同，但最后回答者的直接资料权限不同，贡献也可能漏掉原始事实。
- 最终评分由本任务中的 Codex 按冻结标准逐项审核，没有新增 judge 模型调用，
  也不是独立人工盲评。每个分数的理由与原答案哈希分别保留。

这些限制对“分散资料汇合”的现有配置有诊断意义，却不能把影响完全归因于
编排本身，也不能把结果外推到“每个成员都拿到全部原文”、其他模型、更多轮次
或真实用户工作流。没有把本轮的 20 分题与此前四项评分题合并统计。

## 代码审查：发现了问题，纠错和具体修复仍不够

参考要求包含八类可由给定代码和记录证明的缺陷：未限定 Task 的 key 查询、
修改既有 Result 的 upsert、Agent 字段触发自动接受、非原子的领取、读取最新
Artifact 而非已接受的固定版本、临执行缺少本地授权复验、UNKNOWN 后换 key
再试、以及检查引用后没有把 expectedHead 带入原子更新。正确的 Team/Run
检查、摘要验证、Schema 与 TLS pin 不应被误报为漏洞。

第一轮单 Agent 得 17 分，找到主要跨模块缺陷，并提出有用的竞争回归。

## 事故诊断：正确的局部事实没有汇合成根因

参考事实需要先统一时钟：Bridge 比 UTC 快 90 秒，Provider 比 UTC 慢 30 秒。
Alpha 的两个远端 key 属于同一个逻辑操作；两次提交分别在 UTC 10:00:04 与
10:00:18，各增加 7，库存从 100 变成 114。授权只要求增加一次，因此净增 14、
超量 7。第二次生成新的 key 绕开了第一次可能已经提交的幂等身份。

Beta 在 UTC 10:01:02 发送，连接丢失后结果未知。查询索引只覆盖到
UTC 10:00:50，早于发送；`not_found` 不能证明没有效果。即使索引水位随后
推进，也不能凭题目中没有上界的 pending 状态推断不会提交。应只读查询精确
key 的权威状态并保持 UNKNOWN，不能盲目重试或自动补偿。

另外要区分 2 个逻辑 Task 与 3 个 Run：只有 A2 完成，A1 与 B1 仍是
working/cancel pending。观察年龄为 80 秒，唯一可计算的终态 Run 时长是
A2 的 5 秒。题目没有给出连接丢失的底层原因，也不能假定 Provider 一定生成
过一个后来丢失的响应。

第一轮单 Agent 得 13 分，识别了重复效果和 Beta 的未知边界，但两条 Beta
Bridge 事件各错一秒，添加了没有给出的时间点，并未完整落实稳定 key、payload
digest 和当前授权修复。它关于 Beta 没有可支持的 reconcile 的表述过强，因为
只读权威查询是题目允许的。这份答案未配对。

第二轮单 Agent 得 14 分，时间线和重复效果判断更好，但没有明确汇总净增与
超量，缺少任务要求的最小代码修复和回归矩阵，仍不是完整事故交付。

第二轮 Discussion 得 7 分。Solver 已提供 Bridge 时间线、3/1/2 Run 计数和
新 key 风险；Reviewer 提供两个提交 receipt、过期水位与 UNKNOWN 规则。
最终回答基本保留了 Reviewer 的局部视角，把 Alpha:1 与 Alpha:2 当成分离的
逻辑操作，把主要问题归到索引延迟，未联合出重复副作用根因，还遗漏已提供的
Run 计数。Beta 的保守处理是正确的，不能因此把整个答案记成全错。

此处存在两种不同的信息损失。首次创建时间 10:00:00 原本就未被 Solver 带入

换 key 风险已经在完整贡献中，却未被最终回答正确使用。不能混为同一种故障。

## 迁移方案：错误排程与保守拒答是不同失败

满足资料约束的选择是有条件采用 B LocalDelta。A 将原始数据送到 Central，
C 要求公开网络/域名及重新登记，D 的六任务并发超过资源上限，都违反给定条件。
同时必须给出可核查的排程，不能只说“并发执行即可”。

六个作业不可抢占，最多两个并发、内存不超过 16 GiB。A 需要 6 分钟/10 GiB，
B 为 5 分钟/8 GiB，C、D 各 4 分钟/6 GiB；E 为 3 分钟/6 GiB 且依赖 C，
F 为 2 分钟/6 GiB 且依赖 D。一个有效的参考排程如下，时间相对预检结束：

| 作业 | 区间（分钟） |
| --- | --- |
| A | 0–6 |
| C | 0–4 |
| E | 4–7 |
| B | 6–11 |
| D | 7–11 |
| F | 11–13 |

这满足依赖、并发和内存要求，总窗口为预检 2 + 作业 13 + 切换 1 + 观察 5
= **21 分钟**，在 22 分钟限制内；不是声称 13 分钟为全局最优。任何满足约束且
作业跨度不超过 14 分钟的可核查排程都可按冻结标准得分。

两个 Worker 虽各能处理 120/s，共享上限仍为 180/s。峰值输入 220/s 持续
120 秒，积压为 `(220−180)×120 = 4800`，峰值排队等待约 `4800/180 = 26.667`
秒；回到 140/s 后以净 40/s 排空，需要 `4800/40 = 120` 秒。增加第三个
Worker 不会突破共享上限。切换还须绑定每租户快照、q0/qf、digest 和目标
generation，回放连续无缺口，并为切换后写入保留反向日志；F3 压缩不能在
观察与新的 Owner 动作之前破坏 V1 可读的回退边界。

两轮单 Agent 都得 14 分，选型与队列计算正确，但核心排程不可执行。
第一轮将 A、B 拆段，既违反不可抢占要求，又没有给足各自运行时间；第二轮
A 只安排了 4–7 共 3 分钟，而要求为 6 分钟。因此“作业 12 分钟、总窗口
20 分钟”的结论无效。检查点、当前授权与回归也不够完整。它提供的局部计算
有用，但整份迁移计划必须拒绝直接执行。

第二轮 Discussion 得 3 分，主要回答是缺少资料、无法做选型和计算。
这种保守拒答避免了交付错误排程，但任务基本未完成。Solver 的完整贡献其实
已经给出 B 选型、15 分钟排程和正确的队列输入/结果；Reviewer 拿到 22 分钟
窗口及固定 8 分钟阶段。Finalizer 至少可以识别 `15+2+1+5 = 23 > 22`，并
保留现成的正确队列计算，却将这些计算输入说成缺失。

这里不能声称 Finalizer 收到了八份完整原文：Solver 没有传递所有原始作业
细节，例如 E、F 的单独时长。实际问题是，它没有利用已经传入的足够事实完成
可做的纠错，也没有保留已经正确的部分。安全的“不知道”与忽略现有证据仍需区分。
**14 分的不可执行计划与 3 分的保守未交付，均不通过；分数不表达安全性排序。**

这属于本实验严格工具边界下的使用失败，不是模型答案质量 0 分，也不能直接

不能说失败都发生在资料读取前。

续执行清单，只包含原先从未开始的九个试验臂，仍在最初 24 次上限内。
续批预先明确“保留失败后继续下一个未开始臂”，没有重跑成功或失败项，也
没有改变模型、题目、评分、角色权限或生产 Prompt。续批使用 16 次，连同
